How parda works

A small program on your machine that every AI request passes through. It masks on the way out and restores on the way back.

your AI tool ──http──▶ parda (127.0.0.1:7390) ──https──▶ AI company
  real data             mask ▸ vault ▸ restore             sees stand-ins only

One request, step by step

  1. Your tool sends its request to parda instead of the AI company, because install pointed its base URL there.
  2. parda reads the JSON body and checks every piece of text: your messages, files the agent read, command output, tool results, the system prompt. It skips structural fields (model names, IDs) and fields that are signed by the provider (thinking blocks), because changing those breaks the next request.
  3. Each find is replaced by a stand-in. The request goes on to the AI company — or to whatever proxy or gateway you used before.
  4. The answer streams back. parda restores stand-ins as each piece arrives and passes it straight on.

The technique for each kind of data

parda chooses automatically. There is nothing to set.

Why secrets aren't simply deleted

Agents edit files by writing their content back. If the AI saw [REDACTED] in your .env file, it would write [REDACTED] back and your key would be gone. A stand-in is swapped for the real key on your machine just before the edit happens, so the file stays intact and the AI company still never sees the key.

Why the same value gets the same stand-in

Each stand-in is a keyed BLAKE3 hash of the value. The key is 32 random bytes in ~/.parda/key, readable only by you, and never sent anywhere. So:

  • the AI can still tell "the same person in two places" from "two different people";
  • a long conversation keeps the same stand-ins from turn to turn, so the AI company's prompt caching keeps working;
  • nobody without your key can work back from a stand-in to the value.

The vault

The table from stand-in to real value lives only in parda's memory. It is never written to disk and is gone when parda stops. After a restart, the next request — which carries the whole conversation again — refills it with the same stand-ins. It is capped at 100,000 entries so memory stays small.

Stand-ins split across a stream

AI answers arrive in small pieces. A stand-in can be cut in half: [PERS in one piece and ON_3f9a2c1d] said in the next. parda holds back only the few characters that could be the start of a stand-in and joins them with the next piece. This also works inside tool calls, where the restored value is escaped so the tool's JSON stays valid.

Telling the model

Models treat unfamiliar placeholders as redactions and may refuse to repeat them. When a request carries stand-ins, parda adds one short note to the system instructions: they are placeholders for values the user already has, to be used exactly as written. Without this note, Claude refused to repeat a masked name in our tests; with it, it worked.

Fails closed

  • parda isn't running: your tool can't connect and shows an error. Nothing is sent.
  • The body isn't JSON, or is compressed: refused with a clear message, because parda can't check it.
  • A WebSocket connection: refused, so tools like Codex fall back to normal HTTPS, which parda can check.
  • Sensitive data in the URL itself: refused, because the address is forwarded as it is (checked after decoding, so %40 counts as @).
  • A request from a web page: refused. Only programs on your computer can use parda.
  • The answer is cut off upstream: your tool sees an incomplete answer or an error, never a clean ending.
  • The AI company or your gateway is unreachable: a clear "parda could not reach …" error.
